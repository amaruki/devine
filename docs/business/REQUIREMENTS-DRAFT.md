# Devine Product Discovery Requirements Draft

## User stories

| ID    | Persona         | Action                                                                                                                           | Business value                                                                                                    |
| ----- | --------------- | -------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| US-01 | Visitor         | Understand Devine’s product hook from the landing page in under 10 seconds                                                       | Users and judges can quickly grasp why the project is memorable and daily.dev-native                              |
| US-02 | Developer       | Create and access a Devine account with username and password                                                                    | Devine can persist personal state securely while leaving room for OAuth providers later                           |
| US-03 | Developer       | Connect, validate, and manage an active daily.dev Personal Access Token                                                          | Devine can use personalized daily.dev Public API data only when the token is usable                               |
| US-04 | Developer       | Use server-persisted demo mode without a daily.dev token                                                                         | Users and judges can try the product without setup while keeping repeatable demo state                            |
| US-05 | Developer       | View a dashboard centered on a rubber duck companion                                                                             | The product feels like a playful learning habit companion, not a metrics dashboard                                |
| US-06 | Developer       | Earn daily energy from reading, curating, discussing, and sharing daily.dev posts                                                | Meaningful learning behavior becomes the core game loop                                                           |
| US-07 | Developer       | See health change based on daily learning progress and missed days                                                               | The duck gives visible, recoverable feedback on learning consistency                                              |
| US-08 | Developer       | See a 7-day seniority level and score breakdown                                                                                  | The user understands their learning maturity and what behaviors shape it                                          |
| US-09 | Developer       | Receive daily, personalized, and weekly quests                                                                                   | Devine gives clear short-term actions that improve learning habits                                                |
| US-10 | Developer       | Earn, store, and use power-ups                                                                                                   | Quest completion feels game-like while seniority remains grounded in real behavior                                |
| US-11 | Developer       | Get a next best action and anti-doomscrolling nudge                                                                              | The user knows what to do next instead of passively consuming more content                                        |
| US-12 | Developer       | Review recent counted activity                                                                                                   | The user can understand what Devine counted and why their state changed                                           |
| US-13 | Developer       | Experience playful duck visuals, speech bubbles, and focused micro-animations                                                    | Devine feels alive, funny, and memorable inside a polished developer UI                                           |
| US-14 | Developer       | Create, view, and soft-delete public static share snapshots                                                                      | The user can share their Devine state safely and revoke public access while preserving auditability               |
| US-15 | Developer       | Have Devine fall back gracefully when daily.dev API data is unavailable                                                          | The app remains reliable during demos and real use                                                                |
| US-16 | Developer       | Store raw activity events, daily pet snapshots, inventory, quests, demo state, audit events, and placeholder daily.dev ownership | Devine can render stable production state and recalculate scoring later when explicitly requested                 |
| US-17 | Developer       | Use daily.dev Public API data within documented API constraints                                                                  | Devine works with official feed, post, search, bookmark, profile, tech stack, pagination, and rate-limit behavior |
| US-18 | Hackathon judge | Complete a 60-second demo path using a prepared judge demo account                                                               | The demo avoids signup friction and still shows the production account-based flow                                 |
| US-19 | Developer       | Use Devine with production-grade safety, retention, and reliability                                                              | The MVP is suitable for deployed usage, not only a local hackathon prototype                                      |
| US-20 | Superadmin      | Provision and reset prepared judge demo accounts                                                                                 | The app owner can keep the 60-second hackathon demo reliable without manual database edits                        |
| US-21 | Developer       | Recover account access using an optional email                                                                                   | Users who choose to add email can regain access without losing their Devine state                                 |
| US-22 | Developer       | Have daily activity evaluated in my locale                                                                                       | Daily caps, health, quests, and seniority windows match the user’s expected day boundary                          |

## Acceptance criteria

| AC ID    | US    | Scenario                       | Expected outcome                                                                                                                                                                                                                                                                                                |
| -------- | ----- | ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| AC-01.03 | US-01 | Landing page scope             | Landing page focuses on narrative and CTA rather than detailed mechanics                                                                                                                                                                                                                                        |
| AC-02.01 | US-02 | Account creation               | User can create a Devine account with a unique username and password                                                                                                                                                                                                                                            |
| AC-02.02 | US-02 | Account login                  | User can log in with username and password                                                                                                                                                                                                                                                                      |
| AC-02.03 | US-02 | Password security              | Passwords are hashed server-side and never stored or exposed in plaintext                                                                                                                                                                                                                                       |
| AC-02.04 | US-02 | Future OAuth compatibility     | Account model does not block adding OAuth providers later                                                                                                                                                                                                                                                       |
| AC-02.05 | US-02 | Account-bound foundation       | Authenticated user-owned records can be associated with the Devine user account, including activity events, daily snapshots, demo state, audit events, and placeholder daily.dev connection ownership                                                                                                           |
| AC-02.06 | US-02 | Auth-required private pages    | Dashboard and settings require an authenticated Devine user                                                                                                                                                                                                                                                     |
| AC-02.07 | US-02 | Public route exception         | Public share snapshot pages remain accessible without authentication                                                                                                                                                                                                                                            |
| AC-02.08 | US-02 | Unauthorized access            | Unauthenticated users attempting private routes are redirected or shown an auth prompt                                                                                                                                                                                                                          |
| AC-02.09 | US-02 | Account isolation              | One user cannot access another user’s token placeholder, private events, inventory, demo state, or private snapshots, verified with RBAC unit tests                                                                                                                                                             |
| AC-02.10 | US-02 | Username uniqueness            | Given a username already exists after normalization, account creation with the same normalized username fails with a clear message and no duplicate account is created                                                                                                                                          |
| AC-02.11 | US-02 | Username rules                 | Usernames are 3 to 24 characters, normalize to lowercase for uniqueness, allow letters, numbers, and underscores, and must start with a letter or number                                                                                                                                                        |
| AC-02.12 | US-02 | Reserved usernames             | Reserved usernames such as admin, api, auth, dashboard, settings, share, demo, support, root, and system cannot be registered                                                                                                                                                                                   |
| AC-02.13 | US-02 | Password policy                | Passwords must be at least 8 characters and include uppercase, lowercase, number, and symbol characters                                                                                                                                                                                                         |
| AC-02.14 | US-02 | Session model                  | Auth uses cookie-backed sessions with JWT validation                                                                                                                                                                                                                                                            |
| AC-02.15 | US-02 | Session claims                 | JWT includes user ID, username, role, session ID, issued-at, expiry, and token version                                                                                                                                                                                                                          |
| AC-02.16 | US-02 | Session expiry                 | Sessions expire after 7 days and are refreshed when the user logs in successfully                                                                                                                                                                                                                               |
| AC-02.17 | US-02 | Optional email                 | User can create an account without email, and recovery features remain unavailable until an email is added                                                                                                                                                                                                      |
| AC-03.01 | US-03 | Token connection               | Authenticated user can submit a daily.dev Personal Access Token from settings                                                                                                                                                                                                                                   |
| AC-03.02 | US-03 | Plus requirement copy          | Settings explains that daily.dev Public API requires an active Plus subscription                                                                                                                                                                                                                                |
| AC-03.03 | US-03 | Token auth format              | Server calls daily.dev with `Authorization: Bearer <token>`                                                                                                                                                                                                                                                     |
| AC-03.04 | US-03 | Token security                 | Token is encrypted server-side with environment-managed encryption keys and is never exposed to the browser                                                                                                                                                                                                     |
| AC-03.05 | US-03 | Active token validation        | Token validation makes an authenticated `GET /feeds/foryou` request and treats a successful response as an active connected token                                                                                                                                                                               |
| AC-03.06 | US-03 | Validation success             | Settings shows connected status only after the active token check succeeds                                                                                                                                                                                                                                      |
| AC-03.07 | US-03 | Validation failure             | Missing token, unauthorized token, non-Plus access, rate-limit, and network failure states show clear, friendly error copy and do not replace a working connection                                                                                                                                              |
| AC-03.08 | US-03 | Disconnect                     | User can disconnect daily.dev and delete the stored token                                                                                                                                                                                                                                                       |
| AC-03.09 | US-03 | Token revocation guidance      | Settings reminds users they can revoke tokens in daily.dev API settings                                                                                                                                                                                                                                         |
| AC-03.10 | US-03 | Later invalid token            | If a connected token later fails validation, Devine shows reconnect guidance and offers demo mode                                                                                                                                                                                                               |
| AC-04.01 | US-04 | Demo mode entry                | Authenticated user can enter demo mode without entering daily.dev credentials                                                                                                                                                                                                                                   |
| AC-04.02 | US-04 | Server-persisted demo state    | Demo persona, simulated activity, and pet state persist across sessions for the same Devine user                                                                                                                                                                                                                |
| AC-04.03 | US-04 | Judge default persona          | Demo mode defaults to Code Monkey                                                                                                                                                                                                                                                                               |
| AC-04.04 | US-04 | Demo personas                  | User can view Copaster, Code Monkey, Scholar, and Philosopher behavior patterns                                                                                                                                                                                                                                 |
| AC-04.05 | US-04 | Demo reset                     | User can reset server-persisted demo state from settings                                                                                                                                                                                                                                                        |
| AC-04.06 | US-04 | API independence               | Demo mode works when daily.dev API requests fail                                                                                                                                                                                                                                                                |
| AC-04.07 | US-04 | Mocked future modules          | Before quests, inventory, or full sharing ship, demo dashboard areas may render clearly labeled demo or mocked states without implying unavailable persisted behavior                                                                                                                                           |
| AC-05.01 | US-05 | Dashboard hierarchy            | Dashboard shows pet hero, speech bubble, core stats, recent activity, onboarding, and demo controls where applicable                                                                                                                                                                                            |
| AC-05.02 | US-05 | Companion prominence           | Rubber duck is visually dominant on the dashboard                                                                                                                                                                                                                                                               |
| AC-05.03 | US-05 | Embedded onboarding            | First-use guidance appears in the dashboard and does not block core use                                                                                                                                                                                                                                         |

| AC-07.01 | US-07 | Target met                     | Daily energy of 50 or more applies +5 health                                                                                                                                                                                                                                                                    |
| AC-07.02 | US-07 | Partial progress               | Daily energy of 30 to 49 applies 0 health change                                                                                                                                                                                                                                                                |

| AC-07.08 | US-07 | Recoverable bottom state       | Hibernating is the lowest state and can be recovered from                                                                                                                                                                                                                                                       |
